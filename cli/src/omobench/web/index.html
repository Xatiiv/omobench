01

Connect & run

Uses the OmoBench CLI

Start and load your model in a local inference server first, then point this panel at it. Any server that exposes streaming OpenAI-compatible /v1/chat/completions on this machine's loopback address works; the two guided recipes are presets, not the limit of what can be benchmarked.

Enter the Windows server's IPv4 loopback address, for example http://127.0.0.1:1234. Requires the updated companion. No LAN listener or firewall change is needed. A bridged run can be submitted: because the server and this runner are different environments, you describe the serving machine yourself in step 03 — nothing WSL can see of the Windows host counts as evidence about it. The bridge's own latency is inside every measured number and is never subtracted, and every bridged result is labelled as such wherever it is shown.

Selecting CPU or GPU records your declaration about the server; it does not configure the server and does not prove which device ran inference. OmoBench's own Python dependencies say nothing about your server's device. Neither device rules a result out: CPU and GPU are equally publishable, and so is a server on Windows measured through the bridge. What a public submission needs is listed under What a public submission will also need below, before you start.

Check tokenizer stays offline and only looks at the shape of the identifier and whether its files are already here. Load tokenizer now actually loads it in the interpreter the benchmark uses — which is where a run otherwise dies, before it sends a single request. It may contact huggingface.co to read the repository, and will tell you before it fetches anything. Model weights are never downloaded by either.

    What a public submission will also need

    Running and publishing are two different things. Nothing here stops the benchmark; it is what the registry will additionally ask for, listed now so you can find it before spending the time rather than afterwards.

          02

          Benchmark

          These are CPU measurements. Package and review them below the same way as a GPU run, or save a local report for your own records. A local report records the workload definition, the model configuration and the execution configuration separately, so a CPU-versus-GPU or machine-versus-machine comparison on the same workload is readable as exactly that.

          03

          Review & submit

          Evidence

          Two separate things. Save local report, above, needs none of this: it exports the measurements this machine recorded, for any model, with no sign-in. Everything below prepares a community submission, which additionally needs a model identity the catalog knows (or a proposal for one), an immutable weights revision, a description of the machine that served the model, and the profile's acceptance thresholds. Packaging uses the existing CLI and registry validator.

          Permissions and privacy

          GitHub's public_repo permission allows writing to public repositories. It does not request access to private repositories. OmoBench uses it for the public fork and submission you review below.

          Your GitHub credential stays in this panel process's memory, for at most eight hours. Signing out or stopping the panel forgets it locally. It does not revoke the app on GitHub.

              The machine that served the model

              Where inference actually happened, which is not always where this panel is running. Each fact is recorded with how it was established: detected on the serving machine, or declared by you. Nothing is filled in from a machine that did not serve the model.

              Propose this model for the catalog

              The model you ran is not in the catalog, so it cannot be published as a catalogued result. You can submit this result with a proposal: a reviewer sees the request and the evidence together. A proposal does not add the model to the catalog, and merging this result would not either.
